# 2026-08-21

## Summary

Resolved the remaining Plugin Check (PCP) filesystem deviations so the plugin
passes the Plugin Check "direct filesystem" sniff and can be published. The
previous decision (documented on 2026-08-20) to keep direct PHP filesystem
calls in `Writer`/`SettingsPage` — because the Writer is a WordPress-agnostic
layer and `WP_Filesystem` does not reliably support atomic `rename` — is now
reversed. All filesystem access is routed through a new `Filesystem` helper (a
thin `WP_Filesystem` wrapper), and the PCP-set of `src/` is now clean (0
errors / 0 warnings).

## Changes

### New: `src/Filesystem.php`
- Lazily initializes `WP_Filesystem()` and the global `$wp_filesystem`, then
  forwards the calls the plugin needs: `isDir`, `isReadable`, `isWritable`,
  `mkdir` (creates nested dirs, since `WP_Filesystem::mkdir()` has no recursive
  mode), `getContents`, `putContents`, `move`, `delete`.
- This is the single WordPress-touching FS access point, so the pure-layer
  principle holds elsewhere. `Writer`, `ScssPhpCompiler`, and `SettingsPage`
  validation route their FS work through it.

### `src/Writer.php`
- `atomicWrite()` now uses `Filesystem::isDir/mkdir/putContents/move/delete`
  instead of `mkdir`/`file_put_contents`/`rename`/`unlink`. The `move()`
  attempt keeps the write as atomic as the transport allows (`rename` where
  supported); it no longer suppresses errors with `@`.

### `src/Compiler/ScssPhpCompiler.php`
- Reads the entry file via `Filesystem::getContents()` instead of
  `file_get_contents()` (removes the last PCP `file_get_contents` warning).

### `src/Settings/SettingsPage.php`
- `renderPage()`: `$_GET['msg']` is now sanitized in place
  (`sanitize_text_field( wp_unslash( $_GET['msg'] ) )`), resolving the
  `ValidatedSanitizedInput` error.
- `validateScssDir()`/`validateCssDir()` use `Filesystem::isDir/isReadable/
  isWritable` instead of `is_dir`/`is_readable`/`is_writable`.

### `.phpcs.xml.dist`
- Removed the `/src/*` exclusion for `WordPress.WP.AlternativeFunctions`
  (direct filesystem sniff) — it now applies to `src/`. It stays lifted for
  `tests/*` because tests use direct FS for setup/teardown and are not shipped.

### `Plugin.md`
- §1/§2: `Scanner`, `Detector`, `Enqueue` remain WordPress-agnostic;
  `Compiler`, `Writer`, and `SettingsPage` validation now read/write through
  the `Filesystem` helper. Added `src/Filesystem.php` to the namespace layout.
- §3 validation, §4 Compiler (`getContents` via Filesystem), §5 Writer (moves
  through `Filesystem::move`, atomic subject to transport), new "Filesystem
  helper" subsection, §10 test split updated.

## Update — fix 3 runtime regressions from the PCP filesystem switch

Review of the `WP_Filesystem` migration surfaced three real bugs. All confirmed
against actual WordPress core source and fixed.

### Issue 1 — `Filesystem::fs()` returns null on the frontend (auto-compile breaks)
- Root cause: `wp-admin/includes/file.php` (which defines `WP_Filesystem()` and
  the filesystem classes) is **not loaded on the frontend**. Auto-compile runs
  in `wp_enqueue_scripts` (frontend), so `function_exists( 'WP_Filesystem' )`
  was false → `fs()` returned null → every `Writer::write()` returned false.
- Fix (`src/Filesystem.php`): when `WP_Filesystem()` is unavailable or fails,
  fall back to loading `class-wp-filesystem-base.php` +
  `class-wp-filesystem-direct.php` from `ABSPATH` and instantiating
  `WP_Filesystem_Direct` directly. File operations now work in every context
  while remaining inside the WP_Filesystem abstraction (PCP stays clean).

### Issue 2 — `Filesystem::move()` cannot overwrite an existing CSS file
- Root cause: `WP_Filesystem_Base::move( $source, $destination, $overwrite = false )`
  returns false when the destination exists and `$overwrite` is falsy. The
  helper called `move( $src, $dst )` without overwrite, so every recompile of an
  existing CSS file failed (the first write worked only because the file didn't
  exist yet).
- Fix (`src/Filesystem.php`): `move()` now passes `overwrite=true`. Trade-off:
  on transports without atomic rename the destination is deleted before the
  move (no longer atomic there) — accepted and documented in `Plugin.md`.

### Issue 3 — key-format mismatch between `Plugin::pairStored()` and `Detector::changedEntries()`
- Root cause: stored fingerprint keys are `"<pairId>:<relPath>"`, but
  `Detector::changedEntries()` looks up by bare `relPath`. `pairStored()`
  returned the full prefixed keys, so the lookup always missed → every entry was
  reported changed every request (auto-compile never skipped unchanged files).
- Fix (`src/Plugin.php`): `pairStored()` now strips the `"<pairId>:"` prefix
  from keys (and keeps legacy unprefixed keys for pair 0), so the returned map
  matches the `relPath` keys the Detector uses.

### Files
- `src/Filesystem.php` (`fs()` fallback + `move()` overwrite)
- `src/Plugin.php` (`pairStored()` key normalization)
- `Plugin.md` (Filesystem helper: frontend fallback + overwrite trade-off;
