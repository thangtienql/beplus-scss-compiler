# 2026-09-04

## Summary

Extended the duplicate `css_dir` guard (2026-08-25) to the case it cannot see:
two pairs with **different** `css_dir` values that still write to the **same
output file** because the directories overlap (nested `css_dir`, or `//`/`.`/
symlink variants of one directory). Two layers changed, both documented in
`Plugin.md` first:

1. **Settings** — at save time each candidate pair's compiled output set is
   computed (scan → `Writer::mirrorPath()` against `realpath(css_dir)`) and
   any intersection with an already-accepted pair registers
   `overlapping_css_dir_<i>`. The revert-to-previous fallback now re-checks
   both string uniqueness and output overlap, so a revert can never
   re-introduce the conflict being rejected.
2. **Enqueue** — the glue dedupes the merged `Style[]` list by URL after the
   `beplus_scss/enqueue` filter (`Enqueue::uniqueByUrl`), so the frontend
   never prints two `<link>` tags pointing at the same file — the runtime
   safety net for overlaps the save-time check cannot predict (legacy
   configs, `beplus_scss/write_path` overrides, files added after save).

## Changes

### `src/Settings/SettingsPage.php`

- `sanitizePairs()` gained a fifth parameter, `$destinationResolver`
  (`callable(string,string):array<int,string>`), injected by the WordPress
  side so the pure function stays unit-testable. After the string-uniqueness
  check, the candidate pair's destination set is intersected with the
  accumulated set of accepted destinations; any hit rejects the row with
  `overlapping_css_dir_<i>`.
- `revertPair()` generalized: the previous value is re-checked against both
  the accepted `css_dir` strings and the accepted destination set before it
  is kept; on either conflict the row is dropped (no extra error — the
  original one stands). The row's destinations are registered on every
  successful acceptance or revert so later rows compare against them.
- New private helpers `intersects()` / `registerDests()` track the accepted
  destination set (dest → pair index).
- `sanitize()` passes the resolver closure: `realpath(css_dir)` canonicalises
  `//`, `.` and symlinked roots so path variants compare equal to the plain
  spelling; guarded with `Filesystem::isDir()` so a revert resolving a
  previous pair whose directories were deleted returns `[]` instead of
  letting `Scanner::scan()` throw. Mapped `overlapping_css_dir_<i>` to the
  translated message "CSS destination directory overlaps the output of
  another pair."

### `src/Enqueue.php`

- New pure `uniqueByUrl( array $styles ): array` — drops later entries whose
  URL was already seen (first occurrence wins, order preserved); non-`Style`
  entries pass through for the glue's `instanceof` guard.

### `src/Plugin.php`

- Glue dedupes by URL right after `apply_filters( 'beplus_scss/enqueue', … )`
  and before the `wp_enqueue_style()` loop.

### `Plugin.md`

- §3 (Validate on Save): pinned the output-overlap rule — candidate pair
  scanned and mapped through `Writer::mirrorPath()` against `realpath(css_dir)`;
  intersection registers `overlapping_css_dir_<i>`; revert re-runs string
  uniqueness **and** overlap; enforced at save time only.
- §6: pinned the post-filter URL dedupe and the `Enqueue::uniqueByUrl()`
  signature.

- `tests/unit/EnqueueTest.php` — 2 new tests for `uniqueByUrl`: keeps first

## Part 2 — Auto-compile gated to logged-in admins (kanban #4)

### Summary

kanban #4 ([BUG] "Auto Compile only work for dev") turned out to be a design
question, not a dev-only gate: the code has no environment check, and
auto-compile fired on **every** frontend page load — logged-in or anonymous.
Approved behavior change: auto-compile now triggers **only** when a logged-in
administrator (`current_user_can( 'manage_options' )` — the capability that
configures the plugin) loads a frontend page. Anonymous visitors and non-admin
roles never compile; they only receive already-compiled CSS through enqueue
when `enqueue` is on.

### Changes

- `Plugin.md` §5 (auto-mode glue): added the `manage_options` guard and the
  rationale (filesystem writes stay off anonymous traffic; CSS updates on the
  next frontend load by an administrator or via the "Compile now" button).
- `src/Plugin.php`: `onEnqueueScripts()` compile block now also requires
  `current_user_can( 'manage_options' )`. The enqueue block is unchanged and
  stays ungated for every visitor.
- `tests/integration/PluginGlueTest.php`: `test_auto_compile_with_stored_...`
  now logs in as admin (`wp_set_current_user( 1 )`); two new tests —
  `test_auto_compile_is_skipped_for_anonymous_visitors` (no CSS file written,
  fingerprint option untouched, no handle registered) and
  `test_auto_compile_runs_for_logged_in_admin` (CSS written, handle
  registered).
