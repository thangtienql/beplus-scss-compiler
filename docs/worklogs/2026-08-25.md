## Part 1 — Bug #1 / Issue #2: Frontend FS_CHMOD constants

### Root Cause

On the frontend, WordPress does not load `wp-admin/includes/file.php`, so
`WP_Filesystem()` is unavailable. `Filesystem::fs()` falls back to
instantiating `WP_Filesystem_Direct` directly after loading the two core
class files. However, the filesystem permission constants `FS_CHMOD_DIR` and
`FS_CHMOD_FILE` — which `WP_Filesystem_Direct::chmod()` accesses — are only
defined inside `WP_Filesystem()`. On PHP 8+, accessing an undefined constant
is a fatal `Error`. The Plugin glue caught this error mid-write, so the
atomic temp file was never renamed to the CSS destination, and the error was
stored in `beplus_scss_last_error`.

### Changes

#### `src/Filesystem.php`

Added a two-constant guard block immediately before
`new \WP_Filesystem_Direct( null )` in the ABSPATH fallback path:

```php
if ( ! defined( 'FS_CHMOD_DIR' ) ) {
    define( 'FS_CHMOD_DIR', ( fileperms( ABSPATH ) & 0777 | 0755 ) );
}
if ( ! defined( 'FS_CHMOD_FILE' ) ) {
    define( 'FS_CHMOD_FILE', ( fileperms( ABSPATH . 'index.php' ) & 0777 | 0644 ) );
}
```

Values mirror the expressions WordPress core uses in
`wp-admin/includes/file.php`. Both guards use `! defined()` so the Admin
path — where `WP_Filesystem()` already sets them — is untouched.

## Part 2 — Improvement / Issue #3: Disallow duplicate `css_dir` across Pairs

### Motivation

When multiple pairs configure the same `css_dir` (e.g. `assets/css`):
1. Any SCSS files sharing the same relative filename (e.g. `main.scss`) in both
   source folders would overwrite each other's compiled output on disk.
2. `Enqueue::styles()` registers each pair with a separate handle
   (`beplus-scss-0-main`, `beplus-scss-1-main`), causing WordPress to emit
   duplicate `<link>` tags pointing to the exact same stylesheet URL.

### Solution

Enforced uniqueness of `css_dir` across pairs during settings sanitization
at the validation boundary.

### Changes

#### `src/Settings/SettingsPage.php`

- In `sanitizePairs()`: added a cross-pair uniqueness check using `$seenCssDirs`.
  Any subsequent pair attempting to reuse an already-seen `css_dir` is flagged
  with error code `duplicate_css_dir_<index>` and reverted to its previous
  valid value (or omitted if none).
- In `sanitize()`: mapped `duplicate_css_dir` error codes to the translated
  message `"CSS destination directory must be unique across pairs."`.

#### `tests/unit/SettingsPagePairsTest.php`

Added 3 new unit test cases covering:
- Subsequent pair duplicate `css_dir` rejection.
- Reversion to previous valid pair upon duplicate submission.
- Successful acceptance of pairs with distinct `css_dir` paths.

#### `tests/integration/SettingsPageTest.php`

Added integration test verifying `sanitize()` rejects duplicate `css_dir`
and attaches the corresponding WordPress settings error.

## Part 3 — Issue #3 hardening: revert re-check, case-insensitivity, dedupe on read

### Gaps found while verifying Part 2

1. **Revert could re-introduce the duplicate.** When a rejected row fell back
   to its previous value, that previous value was appended without checking
   `$seenCssDirs`. Example: stored `[{a, x}, {b, y}]`, submitted `[{a, y}, {b, y}]`
   — pair 1 was flagged duplicate, reverted to `{b, y}`, and the option was
   saved with `y` twice anyway. The same hole existed in the invalid-row and
   blank-one-side revert paths.
2. **Case-sensitive comparison.** `assets/css` and `assets/CSS` point to the
   same directory on case-insensitive filesystems (macOS, Windows) but passed
   validation as distinct.
3. **Duplicates already stored by older versions persisted.** Validation only
   runs on save, so pre-existing duplicate pairs kept overwriting each other
   and emitting duplicate `<link>` tags until manually re-saved.

### Changes

#### `src/Settings/SettingsPage.php`

- `sanitizePairs()`: seen-keys are now `strtolower()`-normalized, and all three
  revert paths (duplicate / invalid / blank-one-side) route through a new
  `revertPair()` helper. The helper appends the previous value only when it
  exists and its `css_dir` (lowercased) was not already accepted — otherwise
  the row is dropped instead of re-introducing the duplication being rejected.
- `storedPairs()`: dedupes `css_dir` case-insensitively on read, first
  occurrence wins, neutralizing duplicates stored by older versions without a
  migration.

#### `tests/unit/SettingsPagePairsTest.php`

Added 4 new unit tests: duplicate-revert that would re-introduce a duplicate
drops the row; invalid-revert ditto; case-insensitive duplicate detection;
`storedPairs()` dedupe via reflection (keeping first, dropping later
case-variants).

#### `tests/integration/SettingsPageTest.php`

Added `test_current_settings_dedupes_legacy_duplicate_pairs`: an option saved
with two pairs sharing a `css_dir` reads back as one pair via
`currentSettings()`.
