# 2026-08-25

## Summary

Fixed Bug #1: auto-compile SCSS failed silently on the frontend, leaving
orphaned `.tmp` files in the CSS directory and never producing or enqueueing
the compiled `.css` file.

## Root Cause

On the frontend, WordPress does not load `wp-admin/includes/file.php`, so
`WP_Filesystem()` is unavailable. `Filesystem::fs()` falls back to
instantiating `WP_Filesystem_Direct` directly after loading the two core
class files. However, the filesystem permission constants `FS_CHMOD_DIR` and
`FS_CHMOD_FILE` — which `WP_Filesystem_Direct::chmod()` accesses — are only
defined inside `WP_Filesystem()`. On PHP 8+, accessing an undefined constant
is a fatal `Error`. The Plugin glue caught this error mid-write, so the
atomic temp file was never renamed to the CSS destination, and the error was
stored in `beplus_scss_last_error`.

## Changes

### `src/Filesystem.php`

Added a two-constant guard block immediately before
`new \WP_Filesystem_Direct( null )` in the ABSPATH fallback path:

```php
if ( ! defined( 'FS_CHMOD_DIR' ) ) {
    define( 'FS_CHMOD_DIR', ( fileperms( ABSPATH ) & 0777 | 0755 ) );
}
if ( ! defined( 'FS_CHMOD_FILE' ) ) {
    define( 'FS_CHMOD_FILE', ( fileperms( ABSPATH . 'index.php' ) & 0777 | 0644 ) );
}
```

Values mirror the expressions WordPress core uses in
`wp-admin/includes/file.php`. Both guards use `! defined()` so the Admin
path — where `WP_Filesystem()` already sets them — is untouched.

### `tests/unit/FilesystemChmodConstantTest.php` (removed)

A unit test file was drafted then removed. The bug manifests only when ABSPATH
is defined but `WP_Filesystem()` is absent (frontend); the unit suite has no
ABSPATH, and the integration suite (wp-env) has WP_Filesystem() available —
neither standard environment would have exercised the test. Coverage is
provided by the E2E verification below instead.
