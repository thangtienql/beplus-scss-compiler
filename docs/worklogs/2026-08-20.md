# 2026-08-20

## Summary

Fixed two admin-notification bugs in the settings page: the core `settings_errors()`
renderer breaking the custom layout, and a stale `msg=compiled` query arg showing a
green toast alongside a red validation error.

## Changes

- `src/Settings/SettingsPage.php`:
  - New `suppressCoreNotices()` (hooked on `current_screen`) removes the core
    `admin_notices → settings_errors` callback on `settings_page_beplus-scss` so the
    default red box never breaks the hero layout.
  - New `captureSettingsErrors()` (hooked on `admin_notices`, max priority): the real
    fix. WordPress runs `options-head.php` — which calls `settings_errors()` **inline**
    (not via a hook) — on every `options-general.php` child page, so removing the
    `admin_notices` callback alone was insufficient. The method captures the
    `settings_errors` transient into the static `$pendingErrors`, deletes the
    transient, and empties `$GLOBALS['wp_settings_errors']` *before* `options-head.php`
    runs, so the core renderer prints nothing inside the hero.
  - New pure static `SettingsPage::toastList()` resolves which toasts to render with
    a fixed priority: validation errors win, then "Settings saved.", then the compile
    message from `?msg=compiled|error`. Pure (no WP calls) so the rules are unit-tested
    without wp-env.
  - `renderPage()` now uses `self::$pendingErrors` (falling back to
    `get_settings_errors()`), renders them as `beplus-toast beplus-toast-error/success`
    inside the layout (after the hero, before the status bar), and emits an inline
    script that strips the `msg` query arg via `history.replaceState` so a later Save
    cannot re-show a stale compile toast.
- `Plugin.md` §3 updated (approved first): validation/save errors render as toasts
  inside the layout; the core `settings_errors()` renderer is neutralized on this
  screen by capturing the transient before `options-head.php` runs; "Settings saved."
  toast on success; `msg` is stripped client-side and errors always win.
- `languages/beplus-scss.pot`: added the new `Settings saved.` string.

## Update — GitHub Actions CI

Added continuous integration that runs the three project checks on every push to
`main` and on every pull request.

### Changes
- New `.github/workflows/ci.yml` with three parallel jobs:
  - `phpcs` (PHP 8.2): `vendor/bin/phpcs --report=checkstyle -q | cs2pr` — `cs2pr`
    is shipped by `shivammathur/setup-php` (`tools: composer, cs2pr`) and posts
    WordPress Coding Standards violations as inline PR annotations.
  - `phpstan` (PHP 8.2): `composer analyse` (level max).
  - `phpunit` (matrix PHP `7.4` / `8.2`): `composer test` — covers the supported
    PHP floor and a modern version; PHPUnit resolves to 9 on 7.4 and 10/11 on 8.2
    via `^9.6 || ^10.5 || ^11.0`.
  - Every job uses `actions/cache@v4` on `vendor` (keyed by `composer.lock` hash).
  - Integration suite deliberately not run in CI (needs wp-env/Docker; runs
    locally) — per decision.
- `README.md`: added the CI badge pointing at the `thangtienql/beplus-scss-compiler`
  workflow.

### Fix — PHPUnit 7.4 matrix job

The committed `composer.lock` pins `phpunit/phpunit 11.5.56`, which requires
PHP `>=8.2` (the lock was generated on a PHP 8.5 machine). On a PHP 7.4 runner,
`composer install` therefore fails before tests even run. The `phpunit` job now
splits the dependency step:

- PHP 8.2 → `composer install` (uses the committed lock, reproducible).
- PHP 7.4 → `composer update` so Composer resolves PHPUnit 9.6 (the last 7.4-
  compatible line, allowed by `^9.6 || ^10.5 || ^11.0`); the other dev deps
  (`phpstan` 2.x, `wpcs`, `phpstan-wordpress`) already support `^7.4 || ^8.0`.

- `vendor/bin/phpcs --report=checkstyle -q .` produces valid checkstyle XML locally.

## Update — multi-pair SCSS→CSS paths

Upgraded the plugin from a single `scss_dir`/`css_dir` pair to **multiple rows**,
each an independent SCSS→CSS mapping. Flags stay plugin-global.

### Design (spec: `docs/superpowers/specs/2026-08-20-multi-pair-paths-design.md`)
- Settings option gains `pairs` = `[{scss_dir, css_dir}, ...]`; legacy
  `scss_dir`/`css_dir` keys migrate into `pairs[0]` (backward compatible).
- Pair id = index in `pairs`. Fingerprints, compiled registry and error entries
  are namespaced `"<pairId>:<relPath>"`; pair 0 also reads legacy unprefixed keys.
- Enqueue handle: `beplus-scss-<pairId>-<slug>` (no collision across pairs).
- `beplus_scss/enqueue` applied once over the merged styles of all pairs.
- Filters `/exclude`, `/write_path`, `/error` gain a trailing `$pairId`.
- Blank rows skipped on save; invalid row keeps its previous value with
  row-specific error code (`bad_scss_dir_<i>` / `bad_css_dir_<i>`).

### Changes
- `src/Settings/SettingsPage.php`: `currentSettings()` exposes `pairs` (+ legacy
  migration via `storedPairs()`); pure static `sanitizePairs()` (injectable fs
  validators, unit-tested); `sanitize()` iterates pairs; `renderFields()` renders
  multiple `.beplus-pair-row` blocks with an "Add pair" button, per-row Remove,
  and a `text/template` row template; new `renderPairRow()`/`renderPairRowTemplate()`.
- `src/Enqueue.php`: `Enqueue::styles()` takes `$pairId`, prefixes handles, filters
  registered files by `"<pairId>:"` prefix (pair 0 also accepts legacy unprefixed).
- `src/Plugin.php`: `onEnqueueScripts()` loops all valid pairs (auto-compile once
  per request, then merge styles and apply `beplus_scss/enqueue` once);
  `handleCompileNow()` compiles all pairs; `compileEntries()`/`compileChangedEntries()`/
  `compileAllEntries()`/`buildStyles()` gain `$pairId`; `pairStored()`,
  `pruneCompiledPaths($cssDir, $pairId)` namespace state; filters pass `$pairId`.
- `Plugin.md` §3/§5/§6/§7/§8 + Appendix A updated (approved first).
- Spec written to `docs/superpowers/specs/2026-08-20-multi-pair-paths-design.md`.

### Tests
- Unit (new): `tests/unit/SettingsPagePairsTest.php` (6 tests) — pure
  `sanitizePairs` rules. `tests/unit/EnqueueTest.php` updated for pair-id handles,
  registry filtering, pair-0 legacy acceptance, distinct-pair collision.
- Integration: `SettingsPageTest` sanitize/migration/blank-skip + render
  multi-row + Add/Remove JS test; `PluginGlueTest` updated signatures/handles and
  new two-pair compile+enqueue test. (wp-env only — run when Docker available.)

### Verification
- `composer lint` ✅ (28/28), `composer analyse` ✅ (max, no errors),
  `composer test` ✅ (42 unit tests).
- Integration suite requires wp-env/Docker — not run locally.

## Update — Stats OUTPUT shows wrong info with multiple pairs

Fixed the OUTPUT stat card, which only ever showed the first pair's `css_dir`.

### Root cause
`renderPage()` used `$settings['css_dir']` — the legacy mirror of
`pairs[0]['css_dir']` — so with 2+ pairs the stat understated the setup.

### Changes
- `src/Settings/SettingsPage.php`: the OUTPUT stat value now reads
  `$settings['pairs']`:
  - 0 pairs → `Not set`
  - 1 pair → the pair's `css_dir`
  - 2+ pairs → `%d outputs` (count of saved pairs)
- `languages/beplus-scss.pot`: added `%d outputs` (with translators comment).
- `tests/integration/SettingsPageTest.php`: two new render tests —
  single pair shows its `css_dir`; two pairs show `2 outputs` and do not show
  the first pair's dir. (Uses regex because rendered HTML has indentation
  whitespace around the stat value.)

### Verification
- `composer lint` ✅, `composer analyse` ✅ (max), `composer test` ✅ (42 unit).
- Render smoke-tested with stubbed WP functions — multi-pair page outputs
  `2 outputs`.
